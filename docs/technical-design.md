# Технический проект production-core

> Актуализация 11.11.2026: этот документ сохраняет историю первых этапов. Текущее состояние запуска и оставшиеся задачи — в [аудите выпуска](release-audit-2026-11-11.md). Главная открывает нынешний форум; почта, Object Storage и SmartCaptcha подключены; TOTP отключён по поручению владельца. При расхождении руководствуйтесь аудитом выпуска и последующими решениями владельца.

Статус: базовая архитектура для WP1; первый инкремент реализуется в `backend/`.

## 1. Архитектурное решение

- Модульный монолит, без микросервисов и SPA на первом этапе.
- Python 3.12, Django 5.2 LTS, PostgreSQL 16.
- Django ORM и миграции; Django Admin для первого рабочего контура контент-администратора.
- Встроенные Django auth, session, CSRF и admin LogEntry как основа; 2FA и расширенный аудит будут отдельными задачами WP2.
- Публичный read-only JSON API без DRF на первом инкременте; при появлении регистрации API-контракты будут версионироваться и валидироваться отдельными схемами.
- Отдельный Docker Compose-проект `siberianforum-platform`; текущий `siberianforum-proto` подключается к новому API через proxy в `server/server.py`.
- SQLite допускается только как локальный fallback при запуске вне Docker; целевая общая среда — PostgreSQL.

## 2. Границы первого инкремента

Реализуется:

- `Forum`: самостоятельные форумы с серией, номером, датами, часовым поясом и публикацией.
- `EventDay`: дни программы без привязки к пятидневной модели ESG.
- `Venue`: площадки форума.
- `Event`: событие с типом, регистрационной политикой, ценой, внешней ссылкой и detail mode.
- `ChoiceGroup` / `ChoiceGroupEvent`: группы выбора и связь событий с ними.
- Административный CRUD через Django Admin с индивидуальными учётными записями Django.
- Публичные endpoints списка опубликованных форумов и программы конкретного форума.
- Health check с реальной проверкой соединения с БД.
- Ограничения БД и модельная валидация ключевых отношений.

Не входит и не считается готовым:

- регистрация, ПДн, билеты, модерация и голосование;
- 2FA, SMTP, worker, PDF, файлы и расширенный аудит;
- перенос существующего контента и замена публичного frontend;
- production-деплой и заявление о прохождении Gate G0/G1/G2.

## 3. Регистрационные политики

Модель поддерживает:

- `none` — запись не требуется;
- `auto` — обычное событие;
- `moderated` — маршрут или биржа;
- `external` — Leader ID или другая внешняя регистрация;
- `invite_only` — только по приглашению.

Политика хранится в событии, а не выводится из его названия. Поэтому ESG и промтур могут использовать один backend с разными правилами.

## 4. Целостность данных

На уровне БД:

- окончание форума позже начала;
- окончание события позже начала;
- уникальность даты и порядкового номера дня в форуме;
- неотрицательная цена и положительный capacity target;
- `0 <= min_selections <= max_selections`;
- уникальность события внутри choice group.

На уровне модели/админки:

- площадка события принадлежит тому же форуму;
- событие в choice group принадлежит тому же дню;
- для `external` обязательна https-ссылка;
- для платного события обязательны цена и пояснение ручной оплаты.

Для будущей регистрации одновременно с этими правилами потребуются транзакционная проверка активных выборов и ограничения на уровне заявки. Одна только модель choice group не доказывает запрет двойной записи.

## 5. API первого инкремента

### `GET /api/v1/health/`

Возвращает `200` при доступной БД или `503` без раскрытия внутренней ошибки.

### `GET /api/v1/forums/`

Возвращает только опубликованные форумы. Черновики и архив не раскрываются.

### `GET /api/v1/forums/<slug>/program/`

Возвращает:

- данные форума;
- опубликованные площадки;
- дни в заданном порядке;
- опубликованные события;
- choice groups с min/max и UUID событий.

Не возвращает email куратора, служебные timestamps и другие административные поля. Для `external` возвращается внешняя ссылка, для платного события — цена и пояснение.

Изменяющие публичные методы отсутствуют. Django Admin находится на `/admin/` и требует отдельную staff-сессию.

## 6. Окружение и секреты

- `DEBUG=1` только для локального compose.
- В production `SECRET_KEY` обязателен; приложение не стартует с development key при `DEBUG=0`.
- `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, параметры PostgreSQL задаются окружением.
- Secure cookies, SSL redirect и HSTS включаются вне debug.
- Пароль PostgreSQL в compose предназначен только для локальной разработки и не является production-секретом.

## 7. Миграция и следующие вертикальные срезы

1. Следующий backend-срез: участник, регистрация, элементы заявки, транзакционный запрет конфликтов и лоты.
2. Затем: email verification, модерация и notification outbox.
3. После этого: ticket/PDF/QR и admin scanner.
4. Голосование подключается к общему форумному контуру отдельным модулем после выбора модели identity.
5. Существующий frontend будет переводиться на API по страницам; fallback в localStorage для production не предусматривается.

Правило миграции: действующий прототип остаётся доступен до полного сквозного сценария новой версии; никаких автоматических переносов реальных ПДн из `server/data` без отдельного согласованного плана.

## 6. Реализованный второй инкремент

После первого инкремента добавлены:

- `Participant`, `Registration`, `EmailChallenge`, `RegistrationItem`, `RegistrationItemLot`, `RegistrationItemHistory`, `Consent`, `NotificationOutbox`;
- `Lot` с HTTPS-ссылкой, видимостью заказчика и настраиваемыми min/max на событии биржи;
- публичные `POST /registrations/submit/`, `POST /registrations/verify/`, `GET /registration/`;
- staff-only реестр заявок и решения `approve`, `reject`, `cancel`, `move`;
- двухэтапная страница `site/promtour/` с программой, анкетой, подтверждением кода и личной ссылкой;
- proxy `/api/v1/*` в текущем `server/server.py`, не меняющий старые демо-endpoints.

Безопасность личной ссылки:

- повторная заявка с чужим email не выдаёт token и не меняет прежние данные;
- выбор применяется только после проверки кода;
- в БД хранится SHA-256 от token, а исходный token возвращается один раз;
- персональные и staff ответы отделены от публичного каталога;
- попытки ввода неверного кода ограничены пятью, код истекает через 20 минут;
- `debug_code` присутствует только в DEBUG.

Серверный selection flow:

1. Нормализация UUID, полей и лотов.
2. Проверка публикации события, регистрационной политики и принадлежности форуму.
3. Проверка min/max каждой choice group.
4. Проверка всех пересечений по времени.
5. Проверка принадлежности и min/max лотов.
6. Применение в транзакции с историей и версией заявки.
7. Постановка summary и кураторских уведомлений в outbox.

При блокировке модерации не используется `select_for_update` вместе с nullable `select_related`: PostgreSQL запрещает такой `FOR UPDATE`. Сначала блокируется сам `RegistrationItem`, связанные объекты читаются внутри транзакции.

Оставшиеся технические ограничения:

- IP rate limiting и голосование реализованы; для production нужна реальная SmartCaptcha;
- публичные submit/verify не используют cookie-авторизацию и требуют production anti-fraud приёмки;
- перевод маршрута доступен через staff API и действие с отдельной формой в `RegistrationItemAdmin`;
- страница использует локальный seed, официальный контент должен быть внесён и утверждён отдельно.

## 7. 2FA и реальная доставка писем

Добавлено:

- `Admin2FAProfile` с подписанным TOTP-секретом и `last_counter` против повторного использования;
- `Admin2FAMiddleware` для `/admin/` и `/api/v1/admin/` с отдельными setup/verify страницами;
- TOTP SHA1, шесть цифр, 30 секунд, один период допустимого сдвига и блокировка после пяти ошибок;
- `NotificationOutbox.status=sending`, `next_attempt_at`, `lock_token`, `locked_at`, `provider_message_id`;
- worker `process_notifications` с `SKIP LOCKED`, пятью попытками, exponential backoff и восстановлением просроченных sending;
- шаблоны email verification, registration summary, moderation request и moderation decision;
- личная ссылка в summary письме; code и personal URL удаляются из payload после отправки;
- Mailpit в Docker-сети для реальной SMTP-проверки, UI на `localhost:8026`;
- production-настройки `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `EMAIL_USE_SSL`, `EMAIL_TIMEOUT`, `DEFAULT_FROM_EMAIL`.

Проверено реальными SMTP-сообщениями: код, сводка, кураторское уведомление и решение модератора. При недоступном SMTP заявка остаётся в очереди; после восстановления письмо доставлено следующей попыткой без дубля.

## 8. Билет, QR и чек-ин

Добавлено:

- `Ticket`: OneToOne с регистрацией, отдельный `public_id`, `active/revoked`, версия и даты выпуска/отзыва;
- `CheckIn`: ticket, сотрудник и timestamp, уникальное ограничение одной общей отметки на билет;

- `qrcode`/Pillow для PNG, ReportLab и DejaVu Sans для PDF A4 с кириллицей;
- PDF и PNG-вложения в summary и moderation decision;
- личные QR/PDF endpoints, доступные владельцу personal token или staff;
- `/admin/check-in/` с камерой через `BarcodeDetector` и ручным вводом UUID/QR URL;

URL-контур разделён: `/api/v1/admin/*` для staff API, `/admin/check-in/*` для страниц сканера, затем catch-all Django Admin. Это предотвращает перехват scanner URLs общей админкой.

Проверено: QR/PDF по личному token, запрет без token, вложения через Mailpit, отсутствие билета до одобрения, выпуск после него, отзыв после отмены, staff login + TOTP, первая и повторная отметки прибытия, уникальное ограничение в PostgreSQL и отображение билета в мобильном Chrome.

Не проверено: физическая камера и сеть на площадке. Перед форумом нужен полевой тест на реальных телефонах и production HTTPS-домене.

## 9. Решение по CRM

По решению заказчика Битрикс24 и любая другая внешняя CRM-интеграция исключены из проекта. Обработка заявок выполняется только в Django Admin и через защищённые XLSX/CSV-выгрузки.

`NotificationOutbox` используется исключительно для email-уведомлений и не является очередью CRM. REST/webhook для Битрикса, `IntegrationOutbox`, remote IDs и маппинг CRM-сущностей не реализуются. Требования исходного ТЗ по Битрикс24 отменены этим решением.

## 15. Отдельный admin-хост и защита входа

`accounts.middleware.Admin2FAMiddleware` разрешает `/admin/` и `/api/v1/admin/` только на хостах из `ADMIN_HOSTS`. На остальных хостах возвращается 404, без редиректа на admin-поддомен. Проверка выполняется до авторизации, поэтому staff API также не доступен через публичный домен.

- `ADMIN_DOMAIN` задаёт отдельный хост: production — `admin.sibforum-tomsk.ru`, локально — `admin.localhost`; `ADMIN_SITE_URL` используется в QR чек-ина. `PUBLIC_SITE_URL` остаётся адресом публичной личной ссылки.
- `ALLOWED_HOSTS` дополняется только разрешёнными admin-хостами; `CSRF_TRUSTED_ORIGINS` — адресом `ADMIN_SITE_URL`.
- Пароль и TOTP обязательны. Существующая страница `/admin/2fa/setup/` выдаёт QR и Base32-ключ, совместимые с Google Authenticator, Microsoft Authenticator и Яндекс.Ключом. Отдельный OAuth не нужен.
- POST `/admin/login/` ограничен 20 попытками на IP за 10 минут с ответом 429. TOTP дополнительно блокируется после пяти ошибок на 5 минут и запрещает повторное использование кода.
- Admin-сессия ограничена 30 минутами с продлением при активности и завершением при закрытии браузера. Cookies остаются host-only, без общего `Domain` для всех поддоменов.
- `client_ip` принимает `X-Real-IP` только при `TRUST_PROXY_IP_HEADER=1`; Nginx перезаписывает этот заголовок адресом клиента. Произвольный `X-Forwarded-For` не используется как безусловно доверенный.
- Nginx имеет отдельные HTTPS virtual hosts для `${DOMAIN}` и `${ADMIN_DOMAIN}`. Публичный хост возвращает 404 для admin-маршрутов. На admin-хосте `sitemap.xml` возвращает 404, `robots.txt` — `Disallow: /`, заголовок — `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`.
- Certbot получает общий SAN-сертификат для обоих доменов, поэтому путь `/etc/letsencrypt/live/${DOMAIN}/` используется обоими virtual hosts.
- IP-whitelist не требуется и не совместим с VPN. Скрытие адреса и запрет индексации не рассматриваются как защита вместо авторизации.

Проверено: основной домен и HTTPS `/admin/` + staff API — 404; admin-хост `/admin/` — 302 на вход, staff API без авторизации — 401; `robots.txt` и `X-Robots-Tag` присутствуют, `sitemap.xml` — 404; TOTP, 429 после 20 попыток, `nginx -t` и production Compose config проходят.
