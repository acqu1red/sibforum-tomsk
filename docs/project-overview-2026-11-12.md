# Карта проекта перед новой записью Телемоста · 12.11.2026

Исходная версия: `0378e0c`. Документ фиксирует устройство проекта и проверенную отправную точку. Новый roadmap требований появится после получения новой записи; требования из ещё не полученного видео здесь не предполагаются.

## Назначение

Платформа проведения Сибирского форума ТПП Томской области. Текущий публичный продукт — V форум по промышленному туризму #ПРОМОТУРТОМСК–2026, 23–24 ноября, Томск. Сайт объединяет программу, людей форума, экскурсии, биржу субконтрактации, конкурс, регистрацию и личный билет. Организатор управляет содержанием, заявками, голосами и прибытием участников через отдельный административный домен.

Основная ценность — единый рабочий процесс мероприятия: посетитель изучает программу и выбирает события, подтверждает почту, получает статусы и билет; организатор редактирует содержание, принимает решения по заявкам и встречает участников. Конкурс может работать независимо от регистрации.

## Ключевые связи и правила

- `Forum → EventDay → Event`; площадки принадлежат форуму. `ChoiceGroup` задаёт ограничения выбора; сервер дополнительно проверяет пересечения времени.
- `Speaker ↔ Event` через `EventSpeaker`: роль и тема относятся к конкретному выступлению. Общая фотография наследуется четырьмя местами; каждое допускает собственный файл, режим отображения и фокус.
- Экскурсии — события типа `route` с предприятиями `RouteEnterprise`. Биржа — событие с лотами и ссылками на технические материалы. Онлайн-оплата не реализована; условия ручной оплаты хранятся у события.
- `Participant → Registration → RegistrationItem`; у элементов собственные статусы и история. Обычные события подтверждаются после почты, модерируемые требуют решения сотрудника.
- Повторная отправка анкеты не должна менять подтверждённую заявку до проверки почты. Личный токен хранится в виде хеша; QR использует отдельный идентификатор билета.
- `Ticket → CheckIn`: чтение QR открывает карточку, прибытие подтверждается отдельным действием; повторная отметка ограничена БД.
- `Contest → Nomination → Nominee`: участие компании принадлежит конкретной номинации, включая её описание и фотографии. `Ballot → VoteSelection` хранит принятые голоса.
- Простой режим голосования использует подписанный идентификатор браузера и ограничение сети; email-режим использует подтверждение почты. Это разные механизмы идентификации.
- Сброс тестовых голосов — отдельное действие руководителя с причиной и журналом. Редактирование содержания само по себе голоса не сбрасывает.
- Регистрация и голосование имеют независимые выключатели Nginx и клиентскую конфигурацию `/deployment-config.json`.
- Сохранение контента меняет `ContentRevision`. Видимая страница проверяет редакцию раз в 15 секунд. Визуальный черновик до сохранения существует только в редакторе.
- Только настроенный владелец `director` управляет сотрудниками. TOTP поддерживается кодом; последний отчёт выпуска фиксирует его отключение по поручению владельца.
- CRM отменена предыдущим решением. Упоминания Битрикс24 в локальном ESG-прототипе не являются задачей подключения CRM текущего форума.

Горизонтального переполнения на проверенном размере окна и при эмуляции 390 px нет; в прочитанных сообщениях консоли главной ошибок и предупреждений нет.
5. На опубликованном `/contest/` загружены 8 номинаций и 79 кандидатов. Никакие бюллетени или заявки для проверки не отправлялись. Сообщение об ограничении уже принятого бюллетеня наблюдалось в изолированном браузерном контексте; при сетевом ограничении оно не доказывает голосование именно этим браузером.
6. Текущий набор Django: обнаружены 50 тестов, 49 прошли, 1 пропущен штатным условием PostgreSQL. Прогон выполнен в одноразовом контейнере `siberianforum-backend:meeting-cloud`, без сети, с исходниками backend только для чтения, временными SQLite и media. Рабочая PostgreSQL не подключалась. Пропущен тест одновременных бюллетеней из одной сети. Django system check: замечаний нет.
7. Найденная `backend/.venv` создана для Windows и не запускается как macOS-окружение; для проверки использован существующий Docker-образ.

Эти проверки задают исходную точку, но не заменяют полный проход CAPTCHA → письмо → билет → физическая камера, повторный нагрузочный замер или проверку всех разрешений через production-аккаунты.

## Наблюдения для последующего технического аудита

- Локальный Python proxy пересылает ограниченный набор заголовков и не переносит `Cookie`, `X-CSRFToken` и `Set-Cookie`. По коду это расходится с потребностями нового голосования; перед сквозным локальным тестом нужен подходящий стенд либо исправление proxy. Это наблюдение по реализации, а не воспроизведённый production-дефект: production использует Nginx.
- Исходный шаблон главной находится в `site/promtour/index.html`. Простая правка только `site/index.html` будет перезаписана при `npm run build`.
- Содержание из CMS, статическое начальное представление и опубликованная сборка — разные слои. Визуальную правку нужно привязывать к тому слою, который реально управляет элементом.
- Ранее подготовленные browser smoke-сценарии содержат фиксированные количества записей и предположения о закрытых формах. Выбирать сценарий нужно под фактический режим стенда; старый smoke не является универсальной проверкой нового выпуска.

## Порядок обработки ожидаемой записи

1. Проверить длительность, дорожки, временные смещения и частоту кадров исходника.
2. Извлечь кадры через 4 секунды, сохраняя таймкод каждого кадра; это соответствует заданным 3–5 секундам. Переходы, короткие указания курсором и неоднозначные участки дополнительно смотреть с меньшим шагом.
3. Подготовить обзорные листы и видеоряд из извлечённых кадров с сохранением исходной временной шкалы, сопоставленный с оригинальным звуком. Отдельные видео- и аудиофайлы сначала синхронизировать по доступным признакам.
4. Получить расшифровку с временными метками. Для каждой правки сопоставить реплику, экран, страницу/элемент сайта и текущую реализацию. Не выдавать неразборчивые места и догадки за подтверждённые требования.
5. Создать отдельную матрицу: ID, таймкод, кадр, реплика/смысл, требование, состояние сейчас, нужное изменение, затронутые файлы или записи CMS, приоритет, зависимости, критерий приёмки и статус.
6. Построить по матрице подробный roadmap: сначала сверка уже сделанного, затем оставшиеся изменения по зависимостям и проверки. Сохранить связь каждого пункта с источником.
7. Выполнять изменения последовательными этапами с обновлением статусов и проверкой в Chrome DevTools. Запись и рабочие расшифровки хранить в приватном каталоге, отдельно от публичных файлов сайта.

Текущее действие после подготовки: ожидание записи и следующих указаний владельца.
